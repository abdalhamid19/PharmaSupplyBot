# تخزين نتائج `order run` في SQLite

مجموعة مستندات تصميم لميزة حفظ أهم مخرجات كل `order run` في قاعدة بيانات
SQLite بدلاً من الاعتماد على قراءة ملفات CSV/XLSX من `artifacts/`.

## الرأي في الفكرة باختصار

الفكرة **صحيحة ومطلوبة**، لكن ليس لأن CSV سيئ — بل لأن السؤال الذي تريد
الإجابة عنه تغيّر. الملف الواحد يجيب على «ماذا حدث في هذا الـ run؟».
السؤال الحقيقي الذي تصفه هو «كيف تغيّر سعر هذا الصنف / خصم هذا المخزن عبر
الـ runs؟» وهذا سؤال يمتد أفقياً عبر عشرات المجلدات. لا يمكن الإجابة عنه
بالملفات إلا بمسح كل مجلد وقراءته في الذاكرة كل مرة.

لكن ثلاث ملاحظات مهمة قبل البدء، وكل واحدة منها تغيّر التصميم:

1. **بيانات «كل المخازن لكل صنف» غير موجودة في أي artifact حالياً.**
   الكود يجلبها فعلاً من Tawreed (`get_store_details`) ثم **يرميها** بعد
   اختيار المخزن. الموجود في CSV هو المخزن/المخازن المختارة فقط.
   → أي استيراد من CSV لن يستطيع إنتاج الجدول المطلوب. لا بد من نقطة
   التقاط جديدة في الكود. التفاصيل في `03_capture_points.md`.

2. **يوجد بالفعل بنية SQLite جاهزة في المشروع** (`src/core/database/`)
   تُستخدم لقرارات المراجعة اليدوية. لا تُنشئ طبقة جديدة — أعِد استخدامها
   مع ملف قاعدة بيانات منفصل.

3. **اسم عمودين في المخرجات الحالية مضلِّل** وسينتقل الخطأ إلى قاعدة
   البيانات إن لم يُصحَّح: `winner_sale_price` هو في الحقيقة سعر الجمهور
   (`retailPrice`) و`winner_Purchase_Price` هو سعر الشراء الفعلي بعد الخصم
   (`salePrice`). التفاصيل في `07_risks_and_decisions.md`.

## القرارات المتفق عليها

| القرار | الاختيار |
|---|---|
| الهدف | تحليل تاريخي + مقارنة runs + تغذية الـ run القادم + مصدر لـ Streamlit |
| تفصيل المخازن | كل المخازن لكل صنف + تمييز الفائز |
| آلية الكتابة | كتابة مباشرة أثناء الـ run + أمر إعادة استيراد/إصلاح |
| موقع القاعدة | ملف مستقل `state/order_runs.db` |
